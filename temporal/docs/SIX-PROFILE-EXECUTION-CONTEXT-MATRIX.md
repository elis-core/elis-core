## Direct answer to the core question (unchanged from the prior pass, now backed by live UID checks in addition to the earlier live systemd checks)

`run_agent()`/`hermes -z` does **not** execute under a profile's intended gateway/service/security context. It is a fresh subprocess that inherits the *calling* process's own UID and cgroup and only selects which logical Hermes profile config to load via `HERMES_PROFILE`. Confirmed today, directly: all five non-GitHub gateways run as uid 1000 with **zero `User=` override and zero OS-level separation from each other or from this Adapter's own caller identity**. Only `elis-github`'s `gh-agentd` broker is a genuinely distinct principal (uid 995, gid 982) — and nothing routes into it; the capability gate correctly refuses to let any Activity reach that gap rather than pretending it's closed.

## Smallest bounded architectural correction identified (not implemented — PM/Advisor decision, per Carlos's explicit instruction not to build a competing credential-routing mechanism)

For the five non-GitHub profiles, real OS-principal separation (if ever required) would mean each Temporal Worker process itself being launched *as* its corresponding `hermes-gateway-elis-<profile>.service`'s identity (e.g. a dedicated systemd unit per Worker, one per profile, each polling only its own queue) rather than one process dispatching subprocess calls under a shared caller identity. That is a real infrastructure decision (more services, more systemd units, more operational surface) — flagged as a finding for PM/Advisor, not built here.

For `elis-github`, the only correct fix is Option-A itself landing (t_5d9a121f) — this project's job is to keep correctly reporting `BLOCKED`/`WAITING_FOR_CAPABILITY` until that's independently confirmed, which it now verifiably does via a real reachability probe rather than trusting static config.
