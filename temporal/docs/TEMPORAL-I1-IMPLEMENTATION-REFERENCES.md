### T2 material design decisions

| ELIS component | Temporal primitive/pattern | Grounding | SDK version applicability | Source file |
|---|---|---|---|---|
| Hermes-failure → Activity-retry mapping | `ApplicationError(type=category, non_retryable=bool)` raised from the Activity; ONE bounded `RetryPolicy(maximum_attempts=4, non_retryable_error_types=[...])` attached at `execute_activity` call sites | Installed SDK: `ApplicationError.__init__` signature confirms `type`/`non_retryable` params; `RetryPolicy.__init__` confirms `non_retryable_error_types: Sequence[str]`. The category-before-failure ordering problem (a retry policy must be chosen BEFORE the Activity runs, but the failure category is only known AFTER) is resolved by matching `ApplicationError.type` against `non_retryable_error_types` — a single policy naming every non-retryable category, not a per-category policy chosen in advance. | Confirmed against 1.31.0 directly | `src/elis_temporal/policies/failure_taxonomy.py`, `src/elis_temporal/activities/hermes_activity.py`, `src/elis_temporal/workflows/routing_workflow.py` |
| Semantic Workflow identity + duplicate-retry prevention | `WorkflowIDReusePolicy.ALLOW_DUPLICATE_FAILED_ONLY` (never plain `ALLOW_DUPLICATE`) | Installed SDK: `list(WorkflowIDReusePolicy)` enumerated directly — `ALLOW_DUPLICATE`, `ALLOW_DUPLICATE_FAILED_ONLY`, `REJECT_DUPLICATE`, `TERMINATE_IF_RUNNING`. Chose `_FAILED_ONLY` specifically so a still-running or already-succeeded ID cannot be duplicated, while a genuinely failed run can be retried under the same ID. | Confirmed against 1.31.0 directly | `src/elis_temporal/policies/workflow_identity.py` |
| Profile concurrency mutex ("one active run per profile") | Long-lived singleton Workflow per profile + `@workflow.update` blocking via `workflow.wait_condition`; get-or-create via `WorkflowIDConflictPolicy.USE_EXISTING` | Installed SDK: `Client.start_workflow` signature confirms `id_conflict_policy` param and `WorkflowIDConflictPolicy` enum (`UNSPECIFIED`/`FAIL`/`USE_EXISTING`/`TERMINATE_EXISTING`); `workflow.wait_condition` signature confirms it can run inside an async Update handler and accepts a `timeout`, raising `asyncio.TimeoutError` (== `TimeoutError` under Python 3.11, this venv's interpreter) on expiry. This is Temporal's own documented "entity workflow as a mutex" shape (not a filesystem lock or a custom dedup table), per the directive's explicit instruction to prefer native mechanisms — grounded here against the SDK's actual capability, not a doc-page example, since no live doc fetch happened this pass (see deviation note above). | Confirmed against 1.31.0 directly; `asyncio.TimeoutError`/`TimeoutError` unification is Python-3.11-specific, not an SDK guarantee — worth re-checking if this venv's Python version ever changes | `src/elis_temporal/workflows/profile_exclusivity_workflow.py`, `src/elis_temporal/policies/concurrency.py` |
| Durable PO approval gate | `@workflow.update` (not `@workflow.signal`) for `approve_gate`, so a rejection (wrong gate / unauthorized actor) can raise `ApplicationError` back to the caller synchronously | Installed SDK: `workflow.update`/`workflow.signal` signatures are near-identical except `update` handlers may return a value and their failures are observable by the caller (`WorkflowUpdateFailedError`), while `signal` handlers are fire-and-forget with no caller-visible failure path. An update was the only one of the two that could satisfy directive section 10's "wrong gate rejected" / "unauthorized actor rejected" requirements with a synchronous caller-visible rejection rather than a silently-dropped signal. | Confirmed against 1.31.0 directly | `src/elis_temporal/workflows/gated_pipeline_workflow.py` |
| Non-Workflow-code exception safety for a pre-Activity policy violation (self-validation) | Catch the plain-Python policy exception inside `@workflow.run` and re-raise as `ApplicationError(..., non_retryable=True)` | Not directly doc-grounded this pass (disclosed) — reasoned from first principles plus this project's own T1 precedent (the Adapter's "never raise a bare exception across a Temporal boundary" convention): an uncaught bare Python exception from Workflow code is a retriable *Workflow Task* failure in Temporal's model (assumed transient/deployment bug, retried indefinitely), not a terminal *Workflow* failure — confirmed behaviorally in this pass's own `test_self_validation_rejected_at_workflow_start`, which would hang/timeout instead of terminating cleanly if the bare exception were left unwrapped. Flagged as a decision worth an explicit doc-page citation from PM/Advisor's own independent check, since it wasn't grounded against a live page here. | Behaviorally confirmed against 1.31.0; not additionally doc-cited | `src/elis_temporal/workflows/gated_pipeline_workflow.py` |
