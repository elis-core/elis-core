| Activity retry behavior on `execute_activity` (no explicit `retry_policy` set) | Default Activity retry policy | https://docs.temporal.io/encyclopedia/retry-policies.md | **Material finding for this architecture specifically**: Temporal's default retry policy is 1s initial interval, 2.0 backoff coefficient, 100s max interval, and — critically — **unlimited maximum attempts** unless the Activity raises a non-retryable error. But `run_agent_activity` (wrapping the Hermes Adapter) **never raises** — every failure mode (Hermes exit-code failure, timeout, missing binary) is encoded as a structured `AgentResult` with a `"failed"`/`"timeout"` status, returned normally, not thrown. **Consequence**: Temporal's own Activity-retry mechanism never actually engages for Hermes-level failures, regardless of retry-policy configuration, because the Activity call always looks like a success to Temporal. Any future retry-on-Hermes-failure behavior has to be built explicitly at the Workflow level (inspecting the returned `status` field and deciding to retry/escalate) — it is **not** something Temporal's Activity retry defaults provide for free here. This is real, load-bearing T2-relevant information, not a formality. | `src/elis_temporal/activities/hermes_activity.py`, `src/elis_temporal/adapter/hermes/adapter.py` |
